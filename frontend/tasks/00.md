## Endpoints do backend

Use exclusivamente os endpoints documentados em `docs/api-routes.md`:

### Login (público)

`POST /api/auth/login`

```json
{
  "email": "maria@exemplo.com",
  "senha": "segredo123"
}
```

Resposta `200`:

```json
{
  "usuario": {
    "id": "uuid",
    "nome": "Maria Silva",
    "email": "maria@exemplo.com"
  },
  "token": "jwt"
}
```

Erros esperados:

- `401`: credenciais inválidas.
- `400`: payload inválido.
- `500`: erro interno.

### Criar conta (público)

`POST /api/auth/register`

```json
{
  "nome": "Maria Silva",
  "email": "maria@exemplo.com",
  "senha": "segredo123",
  "confirmarSenha": "segredo123"
}
```

Resposta `201` com o mesmo formato de `{ usuario, token }` do login.

Erros esperados:

- `409`: e-mail já cadastrado.
- `400`: payload inválido.
- `500`: erro interno.

Observações:

- O backend já retorna token no cadastro; após criar conta, faça login automático
  salvando a sessão e redirecionando para a área privada.
- O token JWT expira em 3 horas. Não existe refresh token.
- Não existe endpoint de recuperação/redefinição de senha. O link “Esqueci minha
  senha” deve manter a aparência da referência, mas **não pode navegar para uma
  tela inexistente**. Renderize-o como desabilitado com aviso “Disponível em
  breve” ou remova a navegação, mantendo o visual.
- Login e cadastro são rotas **públicas**. As demais rotas do app são
  **privadas** e exigem token.

## Rotas públicas e privadas

Configure o roteamento com `react-router-dom` (instale a versão atual compatível
com React 19).

| Rota        | Acesso  | Comportamento                                      |
| ----------- | ------- | -------------------------------------------------- |
| `/login`    | Pública | Se já autenticado, redireciona para `/`            |
| `/cadastro` | Pública | Se já autenticado, redireciona para `/`            |
| `/`         | Privada | Placeholder mínimo de área autenticada             |
| `*`         | —       | Redireciona para `/login` ou `/`, conforme sessão  |

- Crie guards/componentes de rota pública e privada.
- A área privada pode ser um placeholder simples com o nome do usuário e um
  botão “Sair”; não implemente o dashboard real nesta task.
- Ao receber `401` de uma rota privada, limpe a sessão e redirecione para
  `/login`.
- Não coloque lógica de redirecionamento dentro dos componentes de view.

## Arquitetura MVC obrigatória

Organize a feature de autenticação assim (ajuste nomes apenas se necessário,
preservando as camadas):

```text
src/
  features/
    auth/
      model/
        auth.types.ts        # DTOs e tipos de domínio
        auth.service.ts      # chamadas axios de login/register
      controller/
        AuthContext.tsx      # sessão global: usuario, token, login, register, logout
        useLoginForm.ts      # estado/validação/erros do formulário de login
        useRegisterForm.ts   # estado/validação/erros do formulário de cadastro
      view/
        LoginView.tsx
        RegisterView.tsx
        AuthShell.tsx        # layout compartilhado, se fizer sentido
  services/
    api.ts                   # instância única do axios
    auth-storage.ts          # persistência/leitura/limpeza da sessão
  routes/
    AppRoutes.tsx
    PublicRoute.tsx
    PrivateRoute.tsx
```

Regras:

- `view` não importa `axios` nem serviços de dados.
- `controller` orquestra estado, validação, loading, erros e chamadas ao model.
- `model` é TypeScript puro, sem React, com DTOs tipados e funções de API.
- Não use `fetch`, `XMLHttpRequest`, `any` ou enums TypeScript. Use union types.
- Use `import type` para imports de tipos.
- Não duplique a lógica de sessão em cada tela.

## Infraestrutura de API e sessão

- Instale `axios` se ainda não estiver instalado.
- Crie `src/services/api.ts` com uma única instância:
  - `baseURL` vindo de `import.meta.env.VITE_API_URL`;
  - timeout razoável;
  - interceptor de request adicionando `Authorization: Bearer <token>`;
  - interceptor de response normalizando erros e tratando `401`;
  - nunca hardcode `http://localhost:3333` no código.
- Adicione `VITE_API_URL=http://localhost:3333` ao `.env.example` (crie o arquivo
  se não existir). Não commite segredos.
- Crie `src/services/auth-storage.ts` com funções claras:
  - salvar sessão (`usuario` + `token`);
  - ler token/usuário;
  - verificar autenticação;
  - limpar sessão.
- “Lembrar de mim” no login:
  - marcado: persistir em `localStorage`;
  - desmarcado: persistir em `sessionStorage`;
  - ao salvar em um storage, remover a sessão do outro para evitar duplicidade.
- No cadastro, use `sessionStorage` por padrão, pois a tela não tem “Lembrar de
  mim”.
- Não decodifique o JWT para obter dados do usuário; use o objeto `usuario`
  retornado pelo backend.

## Validação e comportamento dos formulários

### Login

- E-mail obrigatório e com formato válido.
- Senha obrigatória.
- Trim no e-mail; não aplicar trim na senha.
- Exibir erro geral para `401`: “E-mail ou senha incorretos.”
- Erro de rede: “Não foi possível conectar ao servidor.”
- Limpar erros do campo ao digitar.
- Desabilitar o botão enquanto a requisição estiver em andamento e exibir estado
  de loading acessível.
- Em sucesso: salvar sessão conforme “Lembrar de mim” e navegar para `/`.

### Criar conta

- Nome obrigatório.
- E-mail obrigatório e com formato válido.
- Senha obrigatória e com no mínimo 6 caracteres.
- Confirmação obrigatória e idêntica à senha.
- Exibir erro geral para `409`: “Este e-mail já está cadastrado.”
- Validar também o retorno `400` do backend com mensagem amigável.
- Limpar erros ao digitar.
- Desabilitar o botão durante o envio e exibir estado de loading acessível.
- Em sucesso: salvar sessão e navegar para `/`.

### Acessibilidade

- Todo input deve ter label associada com `htmlFor`/`id`.
- Erros devem usar `aria-invalid` e `aria-describedby`.
- Botões de mostrar/ocultar senha devem ter `aria-label` atualizado.
- Foco visível obrigatório.
- Não comunicar erro apenas por cor; incluir texto.
- Respeitar navegação por teclado.
